# Frequently Asked Questions (FAQ)

Honest, evidence-backed technical answers to common questions about SELF.

---

### Is SELF safe to run?
**Within its default Docker container, yes—provided you follow basic host isolation hygiene.**  
SELF runs as root inside its own container namespace (`self-self:latest`), but by default, its only host bind mount is `./workspace` (mounted at `/home/entity`) and `./config` (mounted read-only at `/config`). It has no access to your host filesystem, host Docker socket, or host devices unless you explicitly configure bind mounts in `docker-compose.yml`.

However, the default container has outbound network access via Docker bridge networking, and code generated by the agent executes inside the container without sandboxing beyond the container boundary. For untrusted code execution or stricter isolation, use the `hardened` profile (`docker compose --profile hardened up self-hardened`), which runs as unprivileged user `1000:1000`, drops all Linux capabilities (`cap_drop: ALL`), enforces `no-new-privileges`, sets rootfs read-only, and routes network traffic through an allowlisting egress proxy.

### What does it cost to run?
**Offline tests and soak suites cost \$0.00.** All unit tests, integration tests, and the deterministic 60–200 cycle soak suite run entirely offline against local mocks, simulated bodies (`SimBody`), and scripted replay providers.

**Live autonomous runs cost real API tokens with your configured provider.** To protect against runaway costs, SELF includes an enforced `DailyTokenLedger` (`agent/infra/hardening.py:49`). The ledger persists spending in `workspace/state/daily_token_budget.json` against `SELF_MAX_TOKENS_PER_DAY` (default: 200,000 tokens, resetting at UTC midnight). When the limit is reached, SELF pauses execution cleanly and waits for UTC midnight reset or an operator limit increase. Set `SELF_MAX_TOKENS_PER_DAY` in `.env` to match your budget before running live.

### What can SELF do right now?
- **Explore its container environment:** Inspect OS files, directory trees, installed Python packages, CPU/RAM limits, and hardware metrics.
- **Maintain persistent memory & plans:** Retain verified facts (`state/map.json`), lessons, self notes, and an evolving multi-goal plan (`state/plan.json`) across sessions.
- **Synthesize custom tools:** Write new Python tools (`create_tool`), run automated unittests in an isolated subprocess, subject code to an LLM critic review, and retrieve approved tools by keyword search.
- **Run plugins & slash commands:** Dynamically load plugins with declared sensors, actions, and custom slash commands (like `/pet` in `pet_companion`).
- **Self-develop plugins with stop-loss:** Scaffold plugin drafts in `workspace/plugin_dev/`, track expenditure in `state/cost_ledger.jsonl`, and pause at 25%, 50%, and 100% stop-loss checkpoints.
- **Maintain a persistent identity record:** Preserve an evidence-backed record of its name, operating voice, and observed traits without claiming biological life or feelings.

### What can SELF NOT do?
- **It is not conscious, sentient, or alive:** SELF is an LLM-driven program running in a container. Its identity files are technical operating records, not subjective experiences.
- **It cannot grant itself host privileges:** It cannot access host paths, modify `.env` files, open listening host ports, or create cloud provider accounts. Requests for outside capabilities are written to `workspace/state/capability_requests.md` for human review.
- **It cannot modify its core image code:** `/opt/agent/` is owned by `root:root` and mounted read-only (`0444`/`0555`). The agent can only submit unified diff patches to `workspace/state/proposed_patches/` via `propose_core_patch`.
- **It cannot activate unpromoted plugin drafts:** Drafts in `workspace/plugin_dev/` are strictly ignored by the plugin loader; only an operator can promote drafts to `workspace/plugins/` and pin their hash in `config/plugins.json`.
- **It has not been verified in multi-cycle live production:** The current release candidate (`core-v0.1.0-rc3`) has been verified via unit tests and scripted soak replay, but has not undergone a multi-cycle live run with real LLM spend.

### How do I stop it?
Hard stop controls always take immediate precedence over autonomous cycles:
1. **Interactive TUI:** Type `/stop` in the prompt pane. SELF completes any active atomic write, checkpoints its handoff to `state/handoff.json`, and halts.
2. **From the host filesystem:** Create a file named `STOP` inside `workspace/` (`New-Item -ItemType File workspace/STOP -Force` or `touch workspace/STOP`). The independent background `StopWatcher` thread detects the file and breaks the loop immediately.
3. **Docker command:** Run `docker compose down` or `docker compose stop self`.

### How do I add or enable a plugin?
1. Place the plugin directory in `workspace/plugins/<name>/` (or scaffold it using `python -m agent.plugins new <name>`).
2. Compute the plugin's SHA-256 digest:
   ```bash
   python -m agent.plugins list
   ```
3. Add the plugin entry to `config/plugins.json` on the host:
   ```json
   {
     "plugins": {
       "<name>": {
         "enabled": true,
         "pinned_hash": "<computed_sha256_hash>"
       }
     }
   }
   ```
4. On the next cycle boundary or session restart, `PluginManager` discovers the plugin, validates compatibility, verifies the pinned hash, and registers its tools.

### How do version numbers work?
SELF maintains two distinct version tracks:
1. **Core Engine Release (`core-v0.1.0-rc3`):** Follows `core-v<major>.<minor>.<patch>[-rcN]`. Tracks releases of the complete autonomous system, loop coordinator, safety boundaries, container Dockerfile, and operator tooling.
2. **Plugin API Specification (`1.1.0`):** Tracked in `VERSION` and `CORE_API_VERSION`. Follows strict SemVer:
   - **Major (1.x.x -> 2.0.0):** Breaking changes to plugin manifest schema, tool registration APIs, or lifecycle hooks.
   - **Minor (1.0.0 -> 1.1.0):** Backwards-compatible additions (e.g. adding slash command support or self-development pipeline).
   - **Patch (1.1.0 -> 1.1.1):** Backwards-compatible bug fixes.
Plugins declare compatible ranges in `plugin.json` (e.g. `core_api: ">=1.1.0,<2.0.0"`).
