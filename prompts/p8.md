PROMPT 08: Implementation briefing and architecture documentation (read-only, no behavior changes)

Context: I am turning the "self" repo into a reusable core with plug-and-unplug specializations (an antivirus, a robot/IoT body). The person helping me plan the next prompts is an AI assistant that cannot see the repo, so it needs an accurate, evidence-based picture of the current implementation. Your job is to investigate and document. Do NOT change agent behavior, prompts, defaults or state.

## Rules
- Read-only for behavior. You may add files under docs/architecture/ and scripts/ only. Do not edit agent/, eval/, Dockerfile, docker-compose.yml or workspace/.
- Evidence only. Tag every claim: [read] you read the code (give path:line), [ran] you ran it and saw the output, [log] you saw it in workspace logs or state, or [inferred] (say why). Anything you cannot determine goes under "Unknown". Do not guess.
- No secrets. Show env var names and defaults, never values of keys or tokens.
- Hidden eval: say only that eval/ exists, how it is isolated from the agent (mounts, network, image) and how to run its tests. Do not copy item contents, checkers, ratings or expected answers into any document.
- The documents must not be readable by the agent: not under agent/, not under workspace/, not copied by the Dockerfile, not mounted by compose. Verify this and show the evidence (Dockerfile COPY lines and compose mounts).
- No live provider calls. Use static reading and the existing tests.
- Put the git commit hash and today's date at the top of every document.

## Documents to write (docs/architecture/, plus an index README.md)
1. 01-repo-map.md: directory tree with a one-line purpose per package and script; entry points; exactly how the agent starts in practice (host vs container, docker compose, Dockerfile layers, which image compose uses, mounts, user, capabilities, network); which modules run on the host and which in the container; a table of every environment variable (name, default, where read, meaning).
2. 02-runtime-loop.md: one cycle step by step (prompt assembly, tool retrieval, tool rounds, reflection, handoff); what "iteration" and "cycle" mean and how they differ; the stop, pause and STOP file flow; the daily-budget pause; every stop reason.
3. 03-tools.md: a table of every tool (name, arguments, return shape, module, core versus body-specific, risk class: reads / writes / executes / network). The create_tool pipeline in detail (critic, tests, schema check, registry, rejection rules). Where agent-made tools are stored and how they load or get rejected. What limits and sandboxing apply to run_shell.
4. 04-state-and-persistence.md: every file under workspace/state and workspace/logs: purpose, writer, reader, schema summary, whether it is loaded into prompts, growth behavior and caps, migrations.
5. 05-llm-and-models.md: the LLM client, BudgetedLLM, the daily ledger, retries and error classes, output ceilings, provider registry, model registry schema; the helper-model system (probes, research, picker/checkpoints, outcomes, ask_model) and how decisions and outcomes are recorded.
6. 06-plan-identity-conversation.md: plan store, handoff, reflection, session; identity store and name_context; conversation manager; human inbox flow; TUI commands; what the agent can and cannot override.
7. 07-safety-and-limits.md: what protects the host and secrets (hardening, egress logging, network allowlist, container privileges, mounts); what the agent can modify (its own code, or tools only); which limits still exist; what is not enforced; prompt-injection paths (file contents, tool output, web research text reaching prompts).
8. 08-events-catalog.md: every event name: emitter (path:line), fields, meaning. Generate it with a script where possible.
9. 09-tests.md: the suites, counts, what is covered and what is not, how to run them in Docker, slow or flaky tests, known gaps, and how eval is isolated.
10. 10-coupling-and-seams.md (the most important one): (a) every place that assumes the body is a Linux container (strings, tools, environment map, paths like /home/entity, systemd assumptions) with path:line; (b) a summary of which packages import which, and any circular dependencies; (c) candidate seams for a "body" interface (sense / act / permissions) and for plugins (tool registry, prompt assembly, plan seeding, identity, memory tagging, state folders). For each seam: the current code that would have to change, difficulty (low / medium / high) and why; (d) what would break if a plugin were unplugged mid-run.
11. 11-known-issues-and-unknowns.md: bugs, dead code, duplicate mechanisms, TODOs, surprising behavior, READMEs that contradict the code, and everything you could not verify.
12. prompts-verbatim.md: the exact text of SYSTEM_PROMPT, STANDING_GOAL, the cycle prompt templates, identity prompt_context, the conversation system prompt, the model-picker prompt and the critic prompt, with path:line for each.
